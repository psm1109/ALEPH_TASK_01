## ① 무엇으로 붙였나

WebAuthn 패스키 인증을 직접 API에 연결하고 `@simplewebauthn/browser`·`@simplewebauthn/server` 라이브러리로 ceremony를 처리했습니다. 인증 데이터와 비공개 자료는 Neon Postgres, API는 Vercel 서버리스 함수, 화면은 Vite 정적 페이지입니다. 별도 인증 서비스는 사용하지 않습니다.

## ② 왜 그걸 골랐나

패스키의 개인키를 서버에 저장하지 않고, 등록된 공개키로 서명을 검증하기 위해 선택했습니다. 브라우저·기기의 기본 패스키 UI를 활용하고 서버는 5분 일회용 challenge, 사용자 검증, 폐기 가능한 세션을 검사합니다. 계정별 자료 조회에는 세션에서 검증한 `account_id`만 사용합니다.

## ③ 어디를 어떻게 고쳤나

| 흐름 | 소스 위치 | 계정 경계 |
| --- | --- | --- |
| 등록 | `passkey-client.js` → `api/passkey/register-options.js` → `api/passkey/register-verify.js` | 첫 계정은 `/setup` 또는 잠금 화면에서 설정 코드로 만듭니다. 이후 새 계정과 추가 패스키는 인증 세션에서만 등록합니다. challenge에 대상·출발 계정과 사용자 ID를 묶습니다. 운영 배포는 이전 등록 흐름입니다. |
| 로그인 | `passkey-client.js` → `api/passkey/authenticate-options.js` → `api/passkey/authenticate-verify.js` | 검증된 credential의 `account_id`로 세션을 발급합니다. |
| 로그아웃 | `script.js` → `api/passkey/logout.js` → `api/_lib/session.js` | 현재 세션의 DB 해시를 삭제하고 쿠키를 만료합니다. |
| 비공개 자료 조회 | `script.js` → `api/private-items.js` → `api/_lib/session.js` | URL·본문 계정값을 신뢰하지 않고 세션 계정으로 필터링합니다. 다른 계정의 `itemId`는 `404`입니다. |

`api/passkey/credentials.js`의 목록·이름 변경·삭제도 세션 계정에 제한했습니다. `db/migrations/20260928_add_passkey_account_isolation.sql`은 기존 credential·세션·자료를 `owner`에 보존하면서 `account_id`를 추가합니다. 운영 Neon SQL Editor에서 이 마이그레이션의 8개 명령이 성공한 화면을 확인했고, 계정 A의 기존 자료 3건이 남아 있음을 조회했습니다.

## ④ 안 열리는 것을 확인한 기록

민감한 credential ID·challenge 원문·세션 쿠키는 기록하지 않습니다. 응답 구조의 값만 남깁니다.

| 확인 | 성공한 요청 → 응답 | 거절된 요청 → 응답 | 증거 수준 |
| --- | --- | --- | --- |
| 로그인 없이 열기 | `GET /` → 공개 소개 첫 화면 표시 | 쿠키 없는 `GET /api/private-items` → 로컬 검사에서 `401 {"error":"패스키 인증이 필요합니다."}` | 공개 첫 화면은 운영 Chrome 및 별도 로그인되지 않은 브라우저에서 확인. 운영 직접 API 비인증 응답은 이번에 미확인. |
| 남의 패스키로 열기 | A 패스키 로그인 → A 자료 번호 1·2·3 표시; B 패스키 로그인 → B의 가상 자료 번호 4 표시 | B 세션 `GET /api/private-items?itemId=1` 및 A 세션 `GET /api/private-items?itemId=4` → 각각 `{"error":"자료를 찾을 수 없습니다."}` | 두 운영 브라우저 탭의 응답 본문 직접 확인. 서버 소스의 `404` 분기와 일치하며 HTTP 상태 자체는 별도 Network 캡처하지 않음. |
| 이미 쓴 질문 재사용 | 새 인증 challenge와 유효 assertion → `200 {"verified":true}` | 같은 ceremony ID 재사용 → `400 {"error":"인증 요청이 만료되었거나 올바르지 않습니다."}` | 이전 카드 3 운영 기록. 이번 계정 분리 버전의 운영 재검증은 미실행. |
| 패스키 삭제 뒤 로그인 | 남은 `구글 계정 패스키` 로그인 → 비공개 기록 3개 표시 | 삭제한 Windows Hello 패스키는 인증 선택 목록에 없고, 취소 뒤 비공개 영역 잠김 | 이전 카드 4 운영 기록. 이번 계정 분리 버전의 운영 재검증은 미실행. |

운영 Neon에서 계정 A와 B에 서로 다른 WebAuthn user ID가 각각 1개 있고, 패스키도 각 1개임을 확인했습니다. 교차 요청 전·B→A 거절 후·A→B 거절 후 `passkey_private_items` 건수는 매번 **A 3건, B 1건**으로 같았습니다. A 세션에서 URL에 B의 실제 `accountId`를 적어 `GET /api/private-items?accountId=<B 계정>`을 열어도 응답은 A의 자료 번호 **1·2·3**뿐이었고 B의 4번 자료는 없었습니다. 계정 ID 원문은 제출 기록에 남기지 않습니다. 요청 본문에 상대 계정을 넣는 경우는 로컬 회귀 검사만 했습니다. 거절을 만드는 서버 위치는 `api/private-items.js`의 세션 계정 조건 및 `404` 분기입니다.

## ⑤ AI와 나

- **AI에게 맡긴 일:** 계정 격리 코드·마이그레이션 초안, 회귀 검사, 요청·응답 기록과 문서 구성을 작성했습니다.
- **내가 직접 판단한 일:** 사용자가 계정 분리 코드를 Git에 푸시하고 운영 Neon SQL을 직접 실행했으며, 검증을 위해 B 패스키를 직접 등록했습니다. 공개 소개의 개인정보 적합성 판단은 아직 받지 못했습니다.
- **AI 제안을 따르지 않은 일:** 이 대화에서 사용자가 거절한 AI 제안은 확인되지 않았습니다. 없는 거절 사례를 만들어 적지 않았습니다.

## ⑥ 아직 못 막은 것

- 새 사용자 ID는 인증된 계정에서 패스키를 등록할 때만 만들 수 있습니다. 인증 계정의 생성 횟수·속도 제한은 아직 없으므로 과도한 사용에 대한 운영 정책은 별도 검토가 필요합니다. 이 새 흐름은 아직 운영에서 확인하지 않았습니다.
- 모든 패스키를 기기에서 잃어버린 계정을 셀프서비스로 복구할 방법이 없습니다. 서버의 마지막 credential 삭제 차단만으로 기기 분실을 해결하지 못합니다.
- 운영 브라우저에서 교차 요청의 거절 본문은 확인했지만 HTTP 상태와 네 가지 확인의 전체 Network 요청·응답은 저장하지 못했습니다.

## 짧은 확인 방법

1. **어디로 가나요:** 공개 결과물 URL의 `나만 보는 자리`로 갑니다. 소스는 위 패스키 브랜치 URL에서 확인합니다.
2. **세 단계 안에 무엇을 하나요:** ① 첫 계정 `testA`를 설정 코드로 등록하고 자기 자료 번호·건수를 기록합니다. ② 로그인 상태의 `패스키 등록`에서 `testB`를 새 ID로 등록하고 B 자료를 확인합니다. ③ 양쪽 세션에서 상대 자료 번호를 직접 요청하고, URL·본문에 상대 `accountId`도 넣어 봅니다. 이 새 등록 순서는 운영 미검증입니다.
3. **무엇이 보이면 통과인가요:** 각 계정의 자기 자료는 `200`, 상대 자료 번호는 `404`, 계정값 변조 목록은 자기 자료만 반환하며, 거절 전후 상대 자료 건수가 같습니다.
4. **안 될 때는 무엇이 보이나요:** 비인증은 `401`, 없는/상대 자료는 `404`, 마지막 패스키 삭제는 `409`입니다. `500`이나 상대 본문 반환은 실패로 기록하고 제출하지 않습니다.
