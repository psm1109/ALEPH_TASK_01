# 카드 5 — 인증 구현 설명서와 제출 상태

기준일: 2026-09-28. 이 문서는 **현재 로컬 구현과 운영에서 이미 관찰한 사실을 구분**합니다. 계정 A/B의 실제 패스키 교차 검증, 계정 분리 마이그레이션 적용, 새 코드 배포는 아직 실행하지 않았습니다. 아래 가상 계정의 자료 문구는 격리 검증을 위해 만든 내용이며 실제 개인정보가 아닙니다. 공개 소개 본문과 외부 링크의 실제 개인정보 포함 여부는 별도 확인이 필요합니다.

## 제출 URL 및 공개 확인

- 결과물 URL: https://aleph-task-t01.vercel.app/
- 소스 URL: https://github.com/psm1109/ALEPH_TASK_01/tree/t08/passkey
- Chrome 일반 창에서 두 HTTPS 주소가 열렸습니다. 결과물 첫 화면은 기존 소개 제목과 내용이며 등록·로그인이 필요하지 않았습니다. 소스 브랜치는 공개 저장소로 표시됐습니다. **새 시크릿 창 검증은 아직 하지 않았습니다.** 소스 URL에는 이 로컬 변경이 포함되지 않습니다.
- 첫 화면에 1번 과제의 소개·강점·가치·나를 이해하는 기준과 비공개 영역이 이어집니다. 기존 공개 내용은 이번 로컬 변경에서 삭제하지 않았습니다.

## ① 무엇으로 붙였나

WebAuthn 패스키 인증을 직접 API에 연결하고 `@simplewebauthn/browser`·`@simplewebauthn/server` 라이브러리로 ceremony를 처리했습니다. 인증 데이터와 비공개 자료는 Neon Postgres, API는 Vercel 서버리스 함수, 화면은 Vite 정적 페이지입니다. 별도 인증 서비스는 사용하지 않습니다.

## ② 왜 그걸 골랐나

패스키의 개인키를 서버에 저장하지 않고, 등록된 공개키로 서명을 검증하기 위해 선택했습니다. 브라우저·기기의 기본 패스키 UI를 활용하고 서버는 5분 일회용 challenge, 사용자 검증, 폐기 가능한 세션을 검사합니다. 계정별 자료 조회에는 세션에서 검증한 `account_id`만 사용합니다.

## ③ 어디를 어떻게 고쳤나

| 흐름 | 소스 위치 | 계정 경계 |
| --- | --- | --- |
| 등록 | `passkey-client.js` → `api/passkey/register-options.js` → `api/passkey/register-verify.js` | 기존 계정은 세션 계정에 추가하고, `newAccount`는 새 UUID와 별도 WebAuthn user ID를 생성합니다. challenge에 대상·출발 계정을 묶습니다. |
| 로그인 | `passkey-client.js` → `api/passkey/authenticate-options.js` → `api/passkey/authenticate-verify.js` | 검증된 credential의 `account_id`로 세션을 발급합니다. |
| 로그아웃 | `script.js` → `api/passkey/logout.js` → `api/_lib/session.js` | 현재 세션의 DB 해시를 삭제하고 쿠키를 만료합니다. |
| 비공개 자료 조회 | `script.js` → `api/private-items.js` → `api/_lib/session.js` | URL·본문 계정값을 신뢰하지 않고 세션 계정으로 필터링합니다. 다른 계정의 `itemId`는 `404`입니다. |

`api/passkey/credentials.js`의 목록·이름 변경·삭제도 세션 계정에 제한했습니다. `db/migrations/20260928_add_passkey_account_isolation.sql`은 기존 credential·세션·자료를 `owner`에 보존하면서 `account_id`를 추가합니다. **이 SQL은 운영에서 미실행입니다.**

## ④ 안 열리는 것을 확인한 기록

민감한 credential ID·challenge 원문·세션 쿠키는 기록하지 않습니다. 응답 구조의 값만 남깁니다.

| 확인 | 성공한 요청 → 응답 | 거절된 요청 → 응답 | 증거 수준 |
| --- | --- | --- | --- |
| 로그인 없이 열기 | `GET /` → 공개 소개 첫 화면 표시 | 쿠키 없는 `GET /api/private-items` → `401 {"error":"패스키 인증이 필요합니다."}` | 공개 화면은 운영 Chrome, 거절은 로컬 핸들러 검사. 운영에서 이 직접 URL은 브라우저가 차단해 이번에 재확인하지 못함. |
| 남의 패스키로 열기 | 계정 A로 `GET /api/private-items` → A의 가상 기록만 반환 | A 세션으로 `GET /api/private-items?itemId=<B 자료 번호>` → `404 {"error":"자료를 찾을 수 없습니다."}`. B→A도 동일 | 양방향 로컬 모의 DB 검사. 실제 두 패스키 운영 요청은 미실행. |
| 이미 쓴 질문 재사용 | 새 인증 challenge와 유효 assertion → `200 {"verified":true}` | 같은 ceremony ID 재사용 → `400 {"error":"인증 요청이 만료되었거나 올바르지 않습니다."}` | 이전 카드 3 운영 기록. 이번 계정 분리 버전의 운영 재검증은 미실행. |
| 패스키 삭제 뒤 로그인 | 남은 `구글 계정 패스키` 로그인 → 비공개 기록 3개 표시 | 삭제한 Windows Hello 패스키는 인증 선택 목록에 없고, 취소 뒤 비공개 영역 잠김 | 이전 카드 4 운영 기록. 이번 계정 분리 버전의 운영 재검증은 미실행. |

계정 격리 로컬 검사에서는 A 자료 1건·B 자료 1건을 사용했습니다. A→B 조회 전후 B 건수 **1→1**, B→A 조회 전후 A 건수 **1→1**입니다. `GET /api/private-items?accountId=<상대 계정>`과 본문의 `accountId`를 함께 보내도 각 세션의 자기 자료 번호만 돌아왔습니다. 이는 `tests/private-boundary.test.js`의 모의 DB 결과이며 **운영 자료 건수 증거가 아닙니다.** 거절을 만드는 서버 위치는 `api/private-items.js`의 세션 계정 조건 및 `404` 분기입니다.

## ⑤ AI와 나

- **AI에게 맡긴 일:** 계정 격리 코드·마이그레이션 초안, 회귀 검사, 요청·응답 기록과 문서 구성을 작성했습니다.
- **내가 직접 판단한 일:** 사용자가 이 대화에서 직접 판단했다고 확인된 선택은 아직 없습니다. 운영 계정 생성과 공개 소개의 개인정보 적합성은 사용자 판단을 기다립니다.
- **AI 제안을 따르지 않은 일:** 사용자에게 제안하고 거절받은 사항은 아직 없습니다. 따라서 없는 거절 결정을 꾸며 쓰지 않았습니다.

## ⑥ 아직 못 막은 것

- 인증된 계정은 `검증 계정 만들기`를 반복할 수 있습니다. 계정 생성 횟수 제한과 속도 제한이 없어 DB에 많은 가상 계정·challenge를 만들 수 있습니다.
- 모든 패스키를 기기에서 잃어버린 계정을 셀프서비스로 복구할 방법이 없습니다. 서버의 마지막 credential 삭제 차단만으로 기기 분실을 해결하지 못합니다.
- 등록·로그인 challenge는 5분 만료이고 재사용은 삭제로 막지만, 운영에서 두 계정 교차 요청을 확인하기 전에는 실제 격리 통과를 주장할 수 없습니다.

## 짧은 확인 방법

1. **어디로 가나요:** 공개 결과물 URL의 `나만 보는 자리`로 갑니다. 소스는 위 패스키 브랜치 URL에서 확인합니다. 계정 격리 검증은 마이그레이션과 새 코드 배포 후 진행합니다.
2. **세 단계 안에 무엇을 하나요:** ① A 패스키로 열고 자기 자료 번호·건수를 기록합니다. ② `검증 계정 만들기`로 B 패스키를 등록하고 잠근 뒤 B로 엽니다. ③ 양쪽 세션에서 상대 자료 번호를 직접 요청하고, URL·본문에 상대 `accountId`도 넣어 봅니다.
3. **무엇이 보이면 통과인가요:** 각 계정의 자기 자료는 `200`, 상대 자료 번호는 `404`, 계정값 변조 목록은 자기 자료만 반환하며, 거절 전후 상대 자료 건수가 같습니다.
4. **안 될 때는 무엇이 보이나요:** 비인증은 `401`, 없는/상대 자료는 `404`, 마지막 패스키 삭제는 `409`입니다. `500`이나 상대 본문 반환은 실패로 기록하고 제출하지 않습니다.
